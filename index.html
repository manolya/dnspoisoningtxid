DNS Cache Poisoning

Forged-reply injection against recursive resolver caches

How an off-path attacker injects a forged record into a resolver cache, the probability model behind the race, the mitigations that defeat it, and the incident-response lifecycle — with interactive, conceptual tools you can poke at.

Part I ☾ DNS resolution & trust

Why a forged answer mattersResolvers accept consistency, not authenticity

People and programs speak in names (www.bank.example); the network routes by address. A recursive resolver walks the DNS tree on your behalf, then caches the answer and hands that same cached answer to everyone who asks, for its TTL.

That caching is the whole prize. Classic DNS has no cryptographic way to ask “who is authorised to assert this record?” A resolver accepts any UDP reply that merely looks consistent:

  • it arrives at the source port the query went out from,
  • it claims the address of the server that was asked,
  • it carries the same 16-bit transaction ID (TXID),
  • it repeats the exact question, and
  • it arrives while the query is still outstanding — first match wins.

Consistency is not authenticity. If an attacker can match those fields, the resolver believes them. Poison one shared resolver once, and every user downstream is directed to an attacker-controlled host until the TTL expires, with no code running on any client.

Part II ☾ The forged-reply race

The race against the real replyOff-path forged-reply flooding

An off-path attacker can’t see your query, so they guess the secrets (TXID + source port) and race a flood of forged replies in before the slower authoritative answer. Win the race, and the forged A record is cached. The real reply arrives late, matches no outstanding query, and is thrown away.

Key point

The attacker never breaks AES, never solves discrete log, never inverts a hash. They exploit a protocol that used a guessable number as if it were a password: a data-origin-authentication failure expressed as a network race.

The only things the attacker doesn’t already know are the TXID and the port. Everything else — server address, the question — is public or guessable. The attacker position matters enormously: an on-path attacker who can read the query off the wire learns the TXID and port directly, so randomness protects nobody against them.

Part III ☾ The Kaminsky technique

Endless chances & the delegation payloadThe 2008 escalation that still echoes in 2026

Lose a race and the real answer gets cached — no more chances until the TTL expires. Kaminsky’s trick: ask for a random, never-cached subdomain each time (a8f1.bank.example, q91z.bank.example…). Every one is a guaranteed cache miss → a fresh outbound query → a brand-new race, as many as you like. The attacker also chose the name, so they know the question exactly.

And the real payload rides in the authority section: a forged NS record —

forged authority section
# "by the way… I run this entire zone"
bank.example.   NS   ns.attacker.example.

Poisoning a single host record redirects one name. Poisoning the NS delegation redirects every future name in the zone (www, mail, login…) to the attacker.

…but only if the resolver accepts that record

The delegation payload is not automatically cached. A careful resolver applies bailiwick and credibility rules: it keeps authority/glue only for the zone the answering server is actually responsible for, and ranks an authoritative answer above an unsolicited add-on. Whether a forged record lands depends on which zone it claims:

bailiwick decision — same payload, two contexts
# Query chain is resolving a8f1.bank.example via the bank.example servers

IN BAILIWICK — may be cached
  authority:  bank.example.      NS  ns.attacker.example.
  # the answering server is within bank.example → plausibly authoritative

OUT OF BAILIWICK — must be dropped
  authority:  example.           NS  ns.attacker.example.
  additional: www.othersite.example.  A  203.0.113.66
  # a bank.example server has no business asserting these → reject

So the Kaminsky payload works by staying just inside bailiwick — forging delegation for the very zone being queried. A resolver that over-trusts unsolicited or out-of-zone records is the one that falls (the exact class of bug behind the 2025–26 CVEs in Part VII).

Why randomness buys you time, not safety

Model one race as drawing from N equally likely (TXID, port) combinations with q blind forged replies. The chance at least one matches is

per-race success probability
P = 1 − (1 − 1/N)^q        # exact, assuming ideal independent randomness
P ≈ q / N                  # good approximation only while q ≪ N
N = 2¹⁶
TXID only (≈ 65,536)
pre-2008 resolvers
N ≈ 2³²
+ random port
≈ 4.29 billion
N = 1
on-path attacker
reads the values → P = 1

Two cautions the numbers hide. First, the effective N can be far smaller than ideal: restricted ephemeral-port ranges, a weak PRNG (predictable TXID/port), NAT port rewriting, or any information leak shrinks it — that is literally the BIND CVE-2025-40780 failure. Second, Kaminsky turns one race into unlimited races, so even a tiny per-race P approaches certain success given enough random-subdomain queries and time. Entropy raises the cost; it does not change whether a forged answer, once accepted, is authentic. That is why the final guardian is cryptographic.

Part IV ☾ Defenses

Three mitigations for cache poisoningLayered defense, weakest to strongest

☄

TXID + source-port randomization

random TXID + port

Forces a blind off-path attacker to match 1 of ~2³² combinations. Stops blind forgery; no effect against an on-path attacker who reads the values. Probabilistic.

✦

Bailiwick checking

in-zone records only

Do not cache unrelated, unsolicited authority. Rejects a server asserting records for zones it is not authoritative for. Blunts the Kaminsky payload, but not an in-zone forgery.

🌙

DNSSEC validation

signed RRsets

The zone signs its RRsets; a validator checks the chain of trust to the root. A forged answer carries no valid signature, so a won race is still rejected. Categorical.

Note

DNSSEC proves authenticity, not privacy — it signs data, it does not hide your queries. DoT/DoH are the mirror: they encrypt the pipe to your resolver but don’t prove the answer is genuine. Different guardians, different powers; real deployments want both.

DNSSEC is not a yes/no switch

Students often read “DNSSEC on” as “every answer is now authenticated.” It isn’t. A validator assigns each response one of four states, and only one of them means “cryptographically trusted.” Walk the chain of trust below and break a link to see how the state changes.

SecureSigned data with an unbroken chain to the anchor. Authenticated — trust it.
InsecureA signed parent proves the child is unsigned (no DS). Accepted, but unauthenticated — exactly as vulnerable as plain DNS.
BogusData that should validate but doesn’t — bad/missing signature, expired RRSIG, or a forgery. Rejected: the validator returns SERVFAIL.
IndeterminateNo applicable trust anchor, or the chain can’t be fetched. The validator can’t decide, so it can’t vouch for the data.

Takeaway: enabling DNSSEC validation protects you on Secure and Bogus answers (trust the first, reject the second). It does not authenticate Insecure zones — most of the namespace is still unsigned — which is why randomisation and bailiwick checking still matter.

Part V ☾ Incident response

Incident-response lifecycle for a poisoning eventNIST SP 800-61, applied to DNS

The NIST SP 800-61 incident-response lifecycle. The offsets below are illustrative pacing for a tabletop exercise, not mandated deadlines — real timelines depend on TTLs, detection maturity, and blast radius.

  1. ☾
    BEFORE · T−∞ · PREPARATION

    Harden before the incident

    Enable source-port randomization and DNSSEC validation. Log every query. Baseline normal answers and SERVFAIL rates. Keep serve-stale ready and a known-good fallback resolver available.

    lab ↔ the target resolver configuration (ENTROPY=on, VALIDATE=on).

  2. ★
    T+0 → T+15m · DETECTION & ANALYSIS

    Detection

    Users report cert warnings or the “wrong site.” The SIEM flags a cached A/NS record that disagrees with the authoritative zone, a spike in odd TXIDs, or a burst of random-subdomain queries (the Kaminsky signature).

    confirm: which names, which resolver, how much TTL is left, attacker position (off-path / on-path / malicious resolver).

  3. ✦
    T+15m → T+1h · CONTAINMENT

    Containment

    Flush the poisoned cache entries and the related delegation. Fail critical names over to a known-good resolver or serve stale from trusted data. Rate-limit or block the forged-reply source if identifiable.

    lab ↔ containment = docker compose down (flush the poisoned cache and the lab network).

  4. ☄
    T+1h → T+4h · ERADICATION & RECOVERY

    Patch, verify, and re-warm

    Patch the resolver to the fixed build, verify port randomization is actually on, turn on DNSSEC validation, restart, then re-warm the cache from the authoritative source and confirm answers match.

    lab ↔ recovery = bring it back up with ENTROPY=on VALIDATE=on and watch poisoning drop to 0.

  5. 🌙
    T+1d → T+7d · POST-INCIDENT

    Post-incident analysis

    Root-cause the event to a CVE or misconfiguration. Add detections (cached-vs-authoritative mismatch, NS-record changes, TXID anomalies). Update the tabletop. Coordinate disclosure if the finding is novel.

    precedents are collected and verified in Part VII — map each to the defense it regresses.

Part VI ☾ Lab

Reproduce the attack in a disposable sandboxDocker · offline · removed in one command

A self-contained DNS environment on one internal Docker network (no route to the Internet, all domains invented): an authoritative server, an intentionally weakened recursive resolver, an off-path attacker, and a client. Observe poisoning succeed, then enable the mitigations and observe it fail.

Scope & ethics

The target is an intentionally weakened teaching resolver; Stage 1 removes TXID/port randomization and answer validation. Everything runs on one disposable, Internet-isolated Docker network with invented domains. There is no source-IP spoofing and no raw-socket flooder, and nothing here functions outside the lab network. Running a forged-reply flooder against a resolver you do not own is a criminal offence (Türkiye: TCK Art. 243–244) and violates university acceptable-use policy. The deliverable is lab_report.md, not a working tool. Teardown removes all state: docker compose down.

The results below are the expected demonstration outcomes for the reference scaffold — the pattern students should reproduce and record, not measurements shipped inside this page. Paste your own run’s counts and logs into lab_report.md.

Read the numbers honestly

“0 in 30 trials” does not measure the success probability — with N ≈ 2³² the expected count in 30 short races is essentially zero, so a clean run is merely consistent with the P = 1 − (1 − 1/N)^q bound, not a measurement of it. To actually observe the bound, shrink N (e.g. restrict the port range) so events become countable, or compute the expected count and compare. Stage 3 is categorical, not statistical: zero follows from signature failure, so one clean trial already demonstrates the mechanism.

Hand-in prompt (core)

In Stage 3 the attacker still won the race, yet nothing was poisoned. Explain the difference between winning the race and being believed — then map each CVE in the table below to the lab stage / defense it regresses to.

Reflection questions

  • Packet. Using the Part I inspector, name every field a forged reply must match, and say which single field the Kaminsky method makes trivial for the attacker to get right.
  • Probability. For N = 2³² and q = 1000 forged replies per window, compute P per window with the exact formula and with the q/N approximation. How many random-subdomain windows give a cumulative success chance above 50%?
  • Bailiwick. Give one forged authority record that a correct resolver caches and one it rejects for the same query, and state the rule that separates them.
  • DNSSEC states. A validating resolver returns SERVFAIL for a bank’s website during a key rollover, while an unsigned blog resolves fine. Classify each as Secure / Insecure / Bogus / Indeterminate and explain the availability trade-off (tie it to the .de event below).
  • On-path vs off-path. Which of the three defenses helps against an on-path attacker, and why do the other two not?
  • Detection. From the investigation drill, list the three trace features you would turn into SIEM rules, and one benign event each might false-positive on.
